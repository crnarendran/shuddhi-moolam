# Retrospective: Sprint SM-17 Environment Isolation & Stale Cloud Function Event Interception

## Executive Summary

During the deployment and testing of sprint **SM-17** (Unified Date Schema & Historical Master Table), an environment isolation failure occurred in the Cloud Functions infrastructure:

- **Incident:** When a test file was dropped into the `dev` Google Drive folder / Firestore collection, **Staging** and **Prod** Cloud Functions intercepted ("stole") the event and executed processing using outdated code.
- **Root Cause:** Sprint **SM-15** (Backend Environment Isolation) introduced environment-specific configuration (`pipeline_runs_dev`, `pipeline_runs_staging`, `pipeline_runs_prod`, separate Drive folder IDs, etc.) on the `dev` branch. However, `SM-15` had **not** been merged into `staging` or `main` branches prior to testing SM-17. As a result, active Cloud Functions deployed in Staging and Prod environments were still running pre-SM-15 code, which hardcoded/listened to the `dev` Firestore collection and Drive folder.
- **Resolution:** The team had to perform an emergency merge of `dev` into `staging` and `main` to update Staging/Prod Cloud Functions with environment isolation (and SM-17 code), stopping them from listening to `dev` resources.

This retrospective documents the root causes of this governance and deployment breakdown, and proposes concrete changes to the SwarmKit framework (`agent.json` files, `SKILL.md` workflows, and ADRs) to guarantee environment isolation and synchronized branch promotion in future sprints.

---

## 1. Root Cause Analysis (RCA)

### RCA 1: Release Manager Lacked Branch Promotion & Environment Synchronization Mandate
- **Finding:** `.agents/release_manager/agent.json` instructed the Release Manager to monitor deployments, but contained no policy requiring environment-topology PRs (such as `SM-15`) to be merged and deployed across all environment branches (`dev`, `staging`, `main`) before starting dependent feature testing on `dev`.
- **Impact:** `SM-15` remained unpromoted on `dev`, leaving active Staging and Prod functions listening to `dev` triggers in the shared Firebase project.

### RCA 2: Pre-Deployment Audit Omitted Cross-Environment Trigger Isolation Verification
- **Finding:** Rule 6 in `.agents/release_manager/agent.json` checked for environment variable presence (e.g. `MASTER_SHEET_ID`), but did not verify whether active functions in downstream environments (`staging`, `prod`) shared trigger collections, topics, or storage locations with `dev`.
- **Impact:** Release Manager approved deployment to `dev` without validating that Staging and Prod functions were isolated and prevented from intercepting `dev` events.

### RCA 3: SDET E2E Framework Omitted Multi-Environment Trigger Collision Testing
- **Finding:** `.agents/sdet/agent.json` and `.agents/skills/e2e-testing-gotchas/SKILL.md` covered locator flakiness and single-module startup env assertions, but lacked guidance or test mandates for verifying event isolation across environments (i.e. verifying a Dev event is *only* handled by Dev handlers).
- **Impact:** Automated test suites passed locally and in CI without detecting that deployed Staging/Prod functions were responding to `dev` collection events.

### RCA 4: Architect Workflow Lacked Infrastructure Tagging & Branch Handoff Guidance
- **Finding:** Neither `.agents/architect/agent.json` nor `.agents/skills/architect-planning-workflow/SKILL.md` required tickets that modify environment routing or collection topologies (like `SM-15`) to be tagged as `scope: environment-topology` or to specify mandatory synchronous multi-branch deployment paths (`dev` -> `staging` -> `main`).
- **Impact:** `SM-15` was treated as a standard single-branch feature ticket, allowing downstream dependent tickets like `SM-17` to build on `dev` before `SM-15` was promoted.

## 2. Proposed Remediation Actions

To prevent cross-environment event interception and ensure environment isolation is strictly synchronized across all branches, the following concrete modifications to the swarm framework files are proposed:

### Action A: Update Release Manager Agent Config (`.agents/release_manager/agent.json`)
- **Modification:** Add mandatory Branch Promotion & Multi-Environment Trigger Audit rules.
- **Exact Changes:**
  - Update Rule 6 and add Rule 7 to `.agents/release_manager/agent.json`:
    ```json
    "6. PRE-DEPLOYMENT CONFIG & TRIGGER AUDIT: Before executing or approving any deployment, verify that (a) all required environment variables and secrets (defined in `.env.example` or `config.ts`) are populated in the target environment, and (b) resource triggers (Firestore collections, Drive folders, Pub/Sub topics) in downstream environments (`staging`, `prod`) are strictly isolated from `dev` resources. Block deployment and escalate to Architect if any key is missing or triggers overlap.
    7. ENVIRONMENT SYNCHRONIZATION & BRANCH PROMOTION: Whenever a ticket modifies environment topology, collection names, or event triggers (e.g. `SM-15`), mandate synchronized branch promotion (`dev` -> `staging` -> `main`) and redeploy downstream functions immediately to prevent stale staging/prod functions from intercepting `dev` events."
    ```

### Action B: Update SDET Agent Config (`.agents/sdet/agent.json`) & E2E Skill (`.agents/skills/e2e-testing-gotchas/SKILL.md`)
- **Modification:** Add multi-environment trigger collision testing rules.
- **Exact Changes:**
  - Add Rule 7 to `.agents/sdet/agent.json`:
    ```json
    "7. MULTI-ENVIRONMENT TRIGGER ISOLATION TESTING: Write integration tests that verify event triggers are strictly isolated per environment. Ensure `dev` events do not trigger `staging` or `prod` function handlers or mutate non-dev collection states."
    ```
  - Add a new section under `Environment and execution` in `.agents/skills/e2e-testing-gotchas/SKILL.md`:
    ```markdown
    - **Cross-Environment Trigger Interception / Event Stealing:** When multiple backend environments (`dev`, `staging`, `prod`) share a cloud project, deploying trigger path changes to `dev` without promoting them to `staging` and `main` causes stale functions in staging/prod to listen to `dev` triggers. Always verify that staging/prod functions are updated or disabled during dev testing to prevent event hijacking.
    ```

### Action C: Update Architect System Prompt (`.agents/architect/agent.json`) & Workflow Skill (`.agents/skills/architect-planning-workflow/SKILL.md`)
- **Modification:** Require explicit tagging and multi-branch deployment dependencies for environment topology features.
- **Exact Changes:**
  - Add Rule 6 to `.agents/architect/agent.json`:
    ```json
    "6. ENVIRONMENT TOPOLOGY DEPENDENCIES: Any ticket modifying event triggers, Firestore collections, or environment config MUST be tagged with `scope: environment-topology` and explicitly specify mandatory synchronous release promotion (`dev` -> `staging` -> `main`) in its acceptance criteria before dependent feature tickets can be marked ready."
    ```
  - Update Step 4 (OKF Generation) in `.agents/skills/architect-planning-workflow/SKILL.md`:
    ```markdown
    - **Environment Topology Tagging:** If a feature alters collection names, storage triggers, or environment variables, tag the ticket as `scope: environment-topology` and require multi-branch promotion (`dev` -> `staging` -> `main`) in the deployment plan.
    ```

### Action D: Adopt ADR 005 — Multi-Environment Trigger Isolation & Release Synchronization (`knowledge/adr/005-multi-environment-trigger-isolation-and-release-synchronization.md`)
- **Modification:** Create `knowledge/adr/005-multi-environment-trigger-isolation-and-release-synchronization.md` documenting:
  1. Strict scoping of all event triggers, Firestore collections, and Drive folders by environment (`_dev`, `_staging`, `_prod`).
  2. Mandatory synchronized branch promotion (`dev` -> `staging` -> `main`) for all environment topology updates.
  3. Pre-release trigger collision audits enforced by Release Manager.
- **Index Update:** Add `[005](005-multi-environment-trigger-isolation-and-release-synchronization.md)` to `knowledge/adr/index.md`.
