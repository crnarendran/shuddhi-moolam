# Retrospective — 2026-08-12

## Context
Shipped SM-30→35 (per-user settings, commodity personalization,
companies/materials, guidance report, in-product docs, Monitor filter fix)
and promoted `dev → staging → main`. The *promotion itself* surfaced several
framework deficiencies that nearly caused a production incident. The feature
work went smoothly; the release process did not.

## What went well
- Docs-first + per-report inline help (`ReportIntro`/`InfoTip`/`help.ts`) kept
  the UX self-explanatory.
- Monitoring-to-completion (release_manager rule 3) was honoured — every deploy
  was watched to a terminal state, which is how the CI test-step regression
  was even noticed.
- Catching the config drift *before* the prod push avoided a real incident.

## Bottlenecks & root causes (framework deficiencies)

### 1. Near-miss: production almost routed to DEV data (CRITICAL)
`functions/src/config.ts` on `dev` only treated `APP_ENV === 'prod'` as
production, but the deploy workflow sets `APP_ENV` from the **branch name**, so
production arrives as `'main'`. A naive `dev → main` promotion would have
pointed prod at the **dev** Drive folder, master sheet, and Firestore
collections.
- **Root cause:** the `APP_ENV='main' ⇒ prod` mapping is an undocumented,
  non-obvious environment invariant. Nothing in `knowledge/` records it, and
  no test asserts it. `dev` had drifted stale on this file because the fix was
  made on `main`/`staging` and never back-merged.

### 2. Branch content drift undetected until promotion time
`dev` and `main` had diverged in source (`config.ts` env handling, webhook
`fileName` capture) because prior fixes landed on `main`/`staging` and were
never back-merged. The release role's pre-deploy audit (rule 6) checks
secrets/triggers but **not source parity between the branch being promoted and
the current production branch.**
- **Root cause:** no mandated `git diff origin/dev...origin/main -- <source>`
  drift check before promotion, and no mandated **post-release back-merge**
  `main → dev`, so drift accumulates every cycle.

### 3. Production deployed WITHOUT running tests, silently
`main`'s `deploy.yml` had the Test step commented out ("Temporarily disabled to
unblock deployment") while `dev`/`staging` had it enabled. Prod deployed
untested for an unknown number of releases. Merges kept silently choosing the
stale workflow.
- **Root cause:** CI workflow files were not held to **branch parity**, and a
  "temporary" test bypass on a protected branch was never tracked or reverted.

### 4. Merge auto-resolution silently regressed critical files
During promotion merges, `git`'s auto-resolution repeatedly picked the wrong
side of `deploy.yml`/`config.ts`. Separately, a `git add -A` during a merge
swept **untracked `scratch/` files** into a staging commit (caught before push).
- **Root cause:** no post-merge verification of critical files
  (`deploy.yml`, `config.ts`, `firestore.rules`) during promotion, and
  `scratch/` is not git-ignored so it is one `add -A` away from being
  committed.

### 5. Commit-message tooling footgun (minor)
PowerShell here-string syntax (`@'...'@`) used inside the Git Bash tool leaked a
literal `@` as two commit subject lines.
- **Root cause:** shell-syntax mismatch; not a framework gap but worth a note.

## Proposed changes (specific file + change)

1. **`.agents/release_manager/agent.json`** — add three rules to
   `system_prompt`:
   - **Rule 9 (Source-parity drift check):** Before promoting, run
     `git fetch` then `git diff --stat origin/<from>...origin/<to>` restricted
     to source (`functions/src`, `dashboard/src`, `firestore.rules`,
     `.github/workflows`). If the *target* (prod) branch has source the source
     branch lacks, STOP — reconcile (back-merge or cherry-pick the missing
     fixes into the source branch) before promoting. Never let a promotion
     silently overwrite production source.
   - **Rule 10 (Post-merge critical-file verification):** After each promotion
     merge and before pushing, explicitly verify `deploy.yml`, `config.ts`, and
     `firestore.rules` match the intended version; never use `git add -A`
     during a promotion merge in a repo with untracked files.
   - **Rule 11 (Post-release back-merge + CI branch-parity):** After a release
     reaches `main`, back-merge `main → dev` so histories re-converge. CI
     workflow files (`deploy.yml`) must be **identical across dev/staging/main**;
     a disabled test/lint gate on a protected branch is a release blocker, not
     a "temporary" state — track it as a ticket if ever bypassed.

2. **`knowledge/infrastructure.md`** — add an **"Environment resolution"**
   section documenting: the deploy workflow sets `APP_ENV = <branch name>`, so
   production is `APP_ENV='main'` (NOT `'prod'`); any env-conditional code MUST
   treat both `'main'` and `'prod'` as production. Cross-link from
   `config.ts`.

3. **`functions/src/config.test.ts`** (new) — assert that with `APP_ENV='main'`,
   `DRIVE_ROOT_FOLDER_ID` / `MASTER_SHEET_ID` / `FIRESTORE_COLLECTION` /
   `HISTORICAL_COLLECTION` resolve to the **production** values (guards against
   a future regression of the env mapping).

4. **`.gitignore`** — add `scratch/` and `functions/scratch/` so throwaway
   diagnostic scripts can never be swept into a commit.

5. **`.agents/skills/architect-planning-workflow`** (or release skill) — note
   that this repo uses **merge-based promotion with cross-tool sessions**;
   promotions are not fast-forwards and require the temp-branch merge +
   verify + back-merge dance until a cleaner model (e.g. PR-based, or
   fast-forward-only with rebase) is adopted. (Optional: propose adopting
   fast-forward-only promotion as a future ADR.)
